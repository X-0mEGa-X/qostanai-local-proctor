# Twelve concise jury answers

Evidence date: 8 October 2026. Captain answers; Member 2 contributes actual observations only when recorded. Refer to `RELEASE_REVIEW.md` for test scope.

1. **What detection accuracy have you measured?** None on human webcam trials. We have 26 passing Python tests, two desktop policy tests, API/Electron checks and earlier blank-frame model execution. Those establish software behavior, not detection accuracy.
2. **Does looking away mean cheating?** No. Sustained down/side signals invite review. Reading, disability, assistive technology or a permitted break may explain them. Accommodations and human judgment are necessary.
3. **Can you prove a student photographed the screen?** No. We detect a phone and apply a bounding-box position/area heuristic. Camera aim and shutter action remain unresolved case gaps.
4. **How does gaze work, and are left/right correct?** We calibrate a median baseline from 20 single-face frames, then use relative head and iris features. Automated synthetic direction tests pass. Participant-left/right signs, glasses and lighting still need human tests.
5. **How do you detect people?** MediaPipe Face Landmarker supplies face count, with up to three faces requested. Temporal rules flag absence or more than one face. We do not claim a custom face detector or identity recognition.
6. **Can someone bypass protection?** Yes. Electron restrictions and an optional Windows hook cover selected actions. Full outside-application control is unfinished. Managed Windows accounts and application policies are deployment work, not configured features.
7. **What happens if the page, camera or storage fails?** End and Ctrl+Shift+Q release the session; the main process can recover after renderer failure, and an independent watchdog releases abandoned sessions. Fake camera/storage failure checks pass. Physical key and camera recovery still need tests. Export in-memory reports before closing if disk writes fail.
8. **Does it work offline, and how fast is it?** The architecture has no cloud inference calls and uses downloaded local models. A disconnected-network human rehearsal is pending. We have no measured webcam FPS or live latency. Processing time and cue-to-alert delay are separate fields in guided reports.
9. **What data do you keep?** Local JSON holds timestamped events, event observations and errors. Guided tests add numeric/categorical samples and human notes. Preview frames stay in memory; there is no app footage recording/upload. Reports need institution-defined access and retention controls before a pilot.
10. **What is original, and which outside tools did you use?** Our contribution is the application integration, calibration and temporal rules, review UI, report workflow and recovery. We use pretrained YOLOv8n/COCO and MediaPipe plus OpenCV/PyTorch, FastAPI and Electron. Codex/ChatGPT assisted code and documents. We disclose these rather than claiming original detector training.
11. **Can the university distribute it immediately?** Distribution needs dependency/model-license review, target-device testing and institutional security/privacy decisions. The architecture lists primary component sources. The current repository is a hackathon prototype, with no compliance certification or signed evidence log.
12. **Has KRU tested it or saved reviewer time?** No completed pilot or saving is established. We propose five consenting volunteers, two laptops and 20-minute practice sessions. We would measure misses, false alerts, timing, release success and reviewer workload. Benefits remain hypotheses.
